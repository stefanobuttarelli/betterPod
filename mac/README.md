# betterPod Share for Mac

The Mac app has three independent workspaces: **Library** edits local audio files, **betterPod** edits the experimental Rust player's library over local Wi-Fi, and **Share** sends songs and albums with an 8-digit code. Library works without a connected betterPod or a share code.

## Local library

1. In **Library**, open an album folder or audio files with **Open folder…** (⌘O), or drop them on the window. Folders include their subfolders.
2. Select tracks with ⌘ or ⇧, or use **Albums** to select several complete albums. Press **Magic** (⇧⌘M) to identify and organize the selection automatically. It groups tracks using album folders and tags, searches MusicBrainz, iTunes and Deezer, checks track names and numbering, and prepares matching metadata and covers. Folder suffixes such as `[FLAC]`, codec details and catalog numbers are cleaned before searching. Matching partial selections update only the selected tracks. Conflicting edition years or covers are preserved rather than guessed. When a match needs correction, use Magic's manual tools to search another edition, edit selected songs or the group, change artwork, or merge into an existing album. These tools return to Magic without leaving the review flow.
3. Review the changes in the table. Each changed field and cover has an **Edited** marker; after saving it has a **Saved** marker. The **Changes** filter shows both. Hover a field to see its previous value. **Save Changes** (⌘S) writes every changed loaded track, including tracks hidden by the album filter. Magic and manual lookup prepare drafts; neither writes files by itself.
4. Manual tools remain available from the toolbar, the Library menu and a track's context menu. **Find Album Details…** starts a search from the folder, tags, filenames, track numbers and count, selects the strongest result and previews its details. Choose a provider or another edition, refine the search, and control whether to apply album tags, track tags and artwork. **Find Cover…** uses the same search with only artwork enabled. Missing fields and unavailable artwork keep the current values.
5. The inspector edits title, artist, album, album artist, genre, year, disc and track numbering for every editable selected track. Shared fields show **Multiple Values** when they differ. Choose a JPEG or PNG cover, remove it, or **Revert Selected Changes**. **Merge into Album…** gives selected tracks the destination's album identity without moving files or replacing song titles. If the destination lacks an album artist, Merge fills it consistently for the destination and incoming tracks, using its sole performer or **Various Artists**. Albums with the same normalized album and album-artist tags group together across folders. Missing album artists use performer and folder context to keep unrelated albums with the same title apart. Untagged albums use their folder identity; CD/Disc subfolders share the album parent.
6. **All Tracks** initially sorts by artist → album → disc → track, with natural filename ordering for missing numbers. Click any column heading to sort ascending or descending. **Remove Selected Tracks** and **Clear Library** remove items from the current view only; the files stay on disk. **Undo Library Removal** restores the removed items and their drafts. The app asks before discarding unsaved edits when opening other files or closing.

MP3, FLAC, Ogg Vorbis and M4A support editing. WAV and AIFF can be viewed only; unsupported or unsafe metadata layouts also show a read-only reason. Manual editing works offline. Online identification sends search text derived from folder names, tags and filenames to the music catalogs and downloads metadata and artwork. Audio files are never uploaded. Magic uses catalog and track-list evidence without an AI account or API key.

Each file is staged beside its original and replaced only after a successful write. Audio and unrelated tags are preserved. A file changed outside the app since opening is refused so it can be reloaded. A batch can partly succeed: successfully saved files refresh, each failure is listed, and failed drafts remain available for correction. Symlinked files are not overwritten.

The local editor remains independent from connected devices. Its files stay on the Mac.

## betterPod over Wi-Fi

This requires the experimental Rust player with Wi-Fi Library support. The classic player and its Share protocol are unchanged.

1. On betterPod Rust, open **Music → Wi-Fi Library** (also available in Settings), then **Start Connection**. It shows a fresh eight-digit code.
2. On the Mac, open **betterPod**, choose **Find betterPod**, select the player and enter its code. Both devices must use the same local network. If discovery is blocked, expand **Enter a local address manually** and enter the IP address and port shown on the player.
3. Browse the library, filter or select several albums, and select one or several tracks. The same artist → album → disc → track order, sortable columns, tag editor and artwork controls work here. **Magic** and **Merge into Album…** work with a current Rust player that advertises album joining support. Older players keep manual metadata and artwork editing and show an update notice. Audio files remain on the player; cover previews load when selected.
4. Run Magic to identify the selection or use its manual corrections. Review the highlighted draft and choose **Save Changes**, shown with a checkmark and text. Metadata, artwork and album membership are written on betterPod and its library refreshes automatically. Joining works across physical folders without moving audio or changing disc numbers. **Album Grouping** has its own Edited/Saved marker; a join remains pending if betterPod saved tags but could not confirm the grouping. Plain Album or Album artist edits clear a conflicting private grouping, while cover edits clear a conflicting chosen cover.
5. Choose **Disconnect** on the Mac or **Stop Connection** on betterPod. Leaving the player page keeps an active connection available. Closing betterPod, moving its music/database, or starting a file transfer revokes it.

No connection starts at launch. Pairing and encrypted traffic run directly on the LAN without a relay, account or audio upload. Codes expire after ten minutes; connected sessions end after thirty minutes of inactivity or eight hours. Only one Mac can connect at a time. Five unsuccessful pairing attempts require starting a new connection.

The current decoder's track, including a paused track, cannot be changed remotely. Select another track or stop playback and refresh. A changed file is refused until reloaded. Interrupted saves are never automatically retried: reconnect and reload first, since a batch may already have been written. Partial failures keep their unsaved drafts. Selecting local files while in the betterPod workspace opens them in the separate local Library editor.

See [the Rust Wi-Fi Library notes](../rust/WIFI_LIBRARY.md) for the protocol and local verification workflow. No build is deployed or published automatically.

## Share

**Share** sends songs and albums from a Mac to a betterPod with an 8-digit code, as a betterPod's own Share does (see [NOTES.md](NOTES.md) for how it is used). It only sends; a betterPod receives with Music → Receive. Its studio background fills the window when resized while the transfer scene stays centered.

How songs travel: one album (or some of its songs) goes as the console sends one; one song shows its title on the betterPod; songs of several albums go with one code, in a folder "From <name>" with a subfolder per album, each with its cover, and a collage of the covers on the betterPod's screen.

## Development

- `core/`: the engine, in Go. The share path reads songs (tags, covers), groups them by album and sends them with magic-wormhole (the vendored wormhole-william, app id `betterpod.xyz/share`). It is the same protocol as `src/ij_share.go`; keep the two in step. The separate `library*.go` files read and safely write local metadata and artwork without starting a share. Built as a C archive for the app; `go run ./mac/core <files…>` sends from the command line, for tests (`BETTERPOD_WORMHOLE_URL`, `BETTERPOD_WORMHOLE_RELAY`, `BETTERPOD_SHARE_CODE`, `BETTERPOD_SHARE_FROM`).
- `App/`: the app, in SwiftUI (macOS 13+). Native navigation, tables, menus and toolbars follow system appearance. macOS 26 uses Liquid Glass for functional chrome; older systems use native material fallbacks. Reduced transparency, increased contrast and reduced motion are respected. Share keeps the console's studio, pedestal, laser and digit tiles in a window-filling scene. `AlbumLookup.swift` searches the [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API), follows its [request limits](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting), and supports iTunes and Deezer metadata and artwork. MusicBrainz covers use the [Cover Art Archive API](https://musicbrainz.org/doc/Cover_Art_Archive/API). `MagicLibrary.swift` groups and identifies selected tracks, compares plausible editions and requires unique track matches before automatically preparing changes.
- `App/Updater.swift`: the app updates itself, as Software Update does on the consoles. At start (and from App → Check for Updates…) it looks for the newest `mac-v…` release on GitHub; Update downloads its zip, checks its size and SHA-256 (the digest GitHub gives for each release file), unpacks it, checks its signature, puts it in place of the app and starts it. So the zip keeps its name, `betterPod-Share-mac-v<version>.zip`. When the app can't replace itself (opened from Downloads, where macOS runs a copy, or in a folder it can't write to), it offers the release's page instead.
- `build.sh`: builds it on a Mac (Go and Xcode's command line tools): a universal app, signed ad hoc (not notarized: macOS asks before the first launch), and its zip.
- `VERSION`: the app's version. `.github/workflows/mac.yml` builds it on each change and makes the GitHub release `mac-v<version>` with `NOTES.md`.
- `tests/check.sh`: runs local Go metadata tests, builds a temporary C archive, and runs Swift lookup and editor-model checks. It requires Go and Xcode's command line tools on `PATH`. Run `sh mac/tests/check.sh` from the repository. Network replies in the lookup checks are fixtures; the checks do not contact online services or publish anything. All temporary build output is removed afterward.
- `tests/check-wifi.sh`: runs the real Rust server against the Mac's Go client on localhost, using disposable audio fixtures. It requires the existing Rust Mac build dependencies and never opens a real music library.

The existing release and updater flow is unchanged. Local development and checks do not create or publish a release.
